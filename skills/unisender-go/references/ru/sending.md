# Отправка транзакционного письма

[English](../sending.md) | [Русский](sending.md)

Источник: [email/send](https://godocs.unisender.ru/web-api-ref#email-send). Проверено 2026-10-26, Web API v1.92.

## Письмо без шаблона

Сохрани запрос в рабочий JSON-файл. Замени примерные адреса и идентификатор операции реальными данными задачи. Примерные адреса `*.invalid` не предназначены для отправки.

```json
{
  "message": {
    "from_email": "robot@example.com",
    "from_name": "Магазин",
    "recipients": [
      {"email": "buyer@example.invalid", "substitutions": {"to_name": "Анна"}}
    ],
    "subject": "Заказ принят",
    "body": {
      "html": "<p>Здравствуйте, {{to_name}}! Заказ принят.</p>",
      "plaintext": "Здравствуйте, {{to_name}}! Заказ принят."
    },
    "idempotence_key": "REPLACE_WITH_STABLE_OPERATION_ID"
  }
}
```

Без `template_id` нужны `from_email`, `subject` и хотя бы `body.html` или `body.plaintext`. Домен отправителя должен быть подготовлен; проверь его через `domain/list`, если готовность неизвестна. Один запрос содержит от 1 до 500 получателей. Каждый объект `recipients` имеет `email`; `substitutions` и `metadata` необязательны. Адреса получателей не видят полный массив как список `To` автоматически.

Сначала покажи preview:

```bash
python3 scripts/unisender_go.py call email/send --data-file message.json
```

После явного поручения отправить именно это письмо этим адресатам используй тот же файл с `--execute`. Не заменяй рабочие адреса тестовыми самостоятельно и не отправляй тест, если пользователь просил только подготовить письмо.

## Существующий шаблон

```json
{
  "message": {
    "template_id": "REPLACE_WITH_TEMPLATE_UUID",
    "recipients": [
      {"email": "first@example.invalid", "substitutions": {"to_name": "Анна"}},
      {"email": "second@example.invalid", "substitutions": {"to_name": "Иван"}}
    ],
    "global_substitutions": {"order_number": "42"},
    "idempotence_key": "REPLACE_WITH_STABLE_OPERATION_ID"
  }
}
```

Пропущенные поля берутся из шаблона; явно переданные заменяют их. Для отправки только по `template_id` клиент не требует дублировать тему, тело и отправителя. Если состав шаблона неизвестен, сначала вызови `template/get` и убедись, что необходимые поля в нём есть.

`template_engine` по умолчанию `simple`; также есть `velocity`, `liquid`, `none`. Локальные `recipients[].substitutions` перекрывают глобальные. Имена переменных: латинская буква в начале, затем латинские буквы, цифры или `_`. Не вставляй непроверенный HTML из пользовательских данных как разметку; экранируй значения там, где это требует выбранный шаблонизатор.

## Вложения и параметры

- `attachments`: объекты с `type` (MIME), `name`, `content` (base64). Имена уникальны и не содержат `/`. Лимит отдельного файла — 7 MB; учитывай раздувание base64 и общий размер JSON.
- `inline_attachments`: те же поля; `name` используется как `cid:NAME` в HTML.
- Запрос целиком — максимум 10 MB. Клиент использует консервативный предел 10 000 000 байт UTF-8, включая base64 и JSON.
- `tags`: до четырёх уникальных строк, до 100 символов каждая.
- `global_metadata` и `recipients[].metadata` позволяют связать письмо с операцией приложения. Для группировки есть `campaign_id`: неотрицательное десятичное целое до 128 бит или UUID, а не произвольное название.
- Не добавляй `bypass_*` или `skip_unsubscribe=1` по умолчанию. Они меняют обработку блокировок/отписок; отдельные возможности требуют согласования с поддержкой.
- Не копируй из примеров документации `track_links=0`/`track_read=0`: отключение отслеживания может требовать включения возможности поддержкой. Укажи их только по задаче пользователя.

## Результат и повтор

Успешный ответ содержит `status: success`, `job_id`, возможно `emails` и `failed_emails` (объект «адрес → причина отказа»). Отчёт должен различать принятых и отклонённых получателей. Клиент возвращает код выхода **3** при непустом `failed_emails`, сохраняя ответ и `job_id`. Это частичный результат: принятые письма могут уже отправляться. Не повторяй запрос на всех адресатов. Если не принят ни один адрес, API может вернуть код ошибки 204.

Для каждой новой логической отправки создай один `message.idempotence_key` длиной до 64 символов и сохрани его в JSON **до вызова** (например, UUID). Повтор той же операции сохраняет и ключ, и исходное содержимое. Не генерируй новый ключ при сетевой ошибке.

Документированная защита отклоняет запрос с тем же ключом в течение **одной минуты**. Это не бессрочная идемпотентность. После таймаута результат неизвестен: сначала выясни состояние по имеющимся `job_id`, метаданным, вебхукам или кабинету. При невозможности сверки сообщи о неопределённости; не отправляй снова автоматически. Для нового отправления после устранения причины нужен осознанный выбор пользователя.

`success` и наличие `job_id` не подтверждают доставку; проверяй [события](delivery.md).
